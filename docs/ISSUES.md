## ISSUE-001 — Публичный пользователь может зарегистрироваться сотрудником

- **Связанные требования:** BR-03, FR-07, NFR-01.
- **Приоритет:** Critical.
- **Предусловие:** пользователь не авторизован.
- **Шаги:** открыть `/accounts/register/`; выбрать роль «Сотрудник»; заполнить должность и остальные поля; отправить форму.
- **Фактический результат:** создаются `UserProfile(role='employee')` и `Employee`; новый пользователь получает интерфейс обработки заказов.
- **Ожидаемый результат:** публичная регистрация создаёт только клиента; сотрудника создаёт администратор.
- **Причина в коде:** поле `role` доступно в `RegistrationForm`, а `register()` доверяет переданному значению.
- **Рекомендация:** убрать `role` из публичной формы, всегда назначать `client`; создание сотрудника оставить Django Admin.
- **Статус:** Открыт.


## ISSUE-002 — GET-запрос на URL покупки изменяет данные

- **Связанные требования:** FR-12, NFR-01.
- **Приоритет:** High.
- **Предусловие:** авторизованный клиент, доступный автомобиль на складе.
- **Шаги:** выполнить GET `/cars/<id>/buy/`.
- **Фактический результат:** создаются `Order` и `OrderItem`, остаток уменьшается.
- **Ожидаемый результат:** GET не меняет состояние; покупка разрешена только POST-запросом с CSRF-защитой.
- **Причина в коде:** `showroom.views.buy_car` не ограничено декоратором `@require_POST`.
- **Рекомендация:** добавить `@require_POST` и автотест ответа 405 на GET.
- **Статус:** Открыт.


## ISSUE-003 — Некорректная цена в query string может вызвать HTTP 500

- **Связанные требования:** FR-02.
- **Приоритет:** Medium.
- **Предусловие:** каталог доступен.
- **Шаги:** открыть `/?min_price=abc` или `/?max_price=abc`.
- **Фактический результат:** строка напрямую передаётся в фильтр DecimalField; возможна ошибка преобразования и HTTP 500.
- **Ожидаемый результат:** параметр отклоняется как невалидный, каталог продолжает работать и показывает сообщение.
- **Причина в коде:** фильтры каталога не используют Django Form и не обрабатывают ошибку преобразования.
- **Рекомендация:** создать `CatalogFilterForm` с `DecimalField(min_value=0)` и проверкой `min_price <= max_price`.
- **Статус:** Открыт.


## ISSUE-004 — Уникальность телефона и email не гарантируется базой данных

- **Связанные требования:** NFR-02.
- **Приоритет:** Medium.
- **Предусловие:** в БД существует клиент или сотрудник.
- **Шаги:** создать вторую запись с тем же телефоном/email через ORM, импорт данных или admin.
- **Фактический результат:** база данных допускает дубли; защита существует только в публичной форме регистрации.
- **Ожидаемый результат:** дубликат отклоняется на уровне БД/модели независимо от точки ввода.
- **Причина в коде:** поля `Client.phone`, `Client.email`, `Employee.phone`, `Employee.email` не имеют общего ограничения уникальности.
- **Рекомендация:** определить модель контакта либо добавить согласованные `UniqueConstraint` и миграцию; обработать `IntegrityError`.
- **Статус:** Открыт.


## ISSUE-005 — Автомобиль с нулевым остатком может отображаться в каталоге

- **Связанные требования:** FR-01.
- **Приоритет:** Low.
- **Предусловие:** автомобиль имеет `stock=0`, но `is_available=True`.
- **Шаги:** открыть главную страницу с каталогом.
- **Фактический результат:** `showroom.views.index` фильтрует только по `is_available=True`, поэтому автомобиль виден.
- **Ожидаемый результат:** автомобиль с нулевым остатком скрыт либо явно помечен отсутствующим.
- **Причина в коде:** `stock` и `is_available` могут рассинхронизироваться при изменении через ORM/admin.
- **Рекомендация:** фильтровать `stock__gt=0` и добавить модельную проверку или централизованный метод обновления остатка.
- **Статус:** Открыт.
## ISSUE-006 — Заказ, оплаченный через корзину, нельзя взять в работу и выдать

- **Связанные требования:** UR-06, FR-15, FR-16; требуется согласовать FR-15 с маршрутом онлайн-оплаты.
- **Приоритет:** High.
- **Предусловие:** зарегистрированы клиент и сотрудник, автомобиль есть на складе.
- **Шаги:** клиент добавляет автомобиль в корзину и оплачивает; сотрудник вызывает `take`, затем `deliver` для созданного заказа.
- **Фактический результат:** заказ создан в `paid` без сотрудника; `take` принимает только `new`, а `deliver` разрешён только закреплённому сотруднику. Заказ остаётся без возможности выдачи через пользовательский процесс.
- **Ожидаемый результат:** администратор/сотрудник имеет предусмотренный системой способ закрепить оплаченный заказ и выдать его без повторной оплаты.
- **Автоматическая проверка:** `tests/test_known_defects.py::test_staff_can_assign_and_deliver_online_paid_order`, `xfail(strict=True)`.
- **Рекомендация:** согласовать требования и диаграмму состояний, разрешить контролируемое назначение свободного оплаченного заказа и добавить его в список доступных сотруднику заказов.
- **Статус:** Открыт; обнаружен при сценарном тестировании ЛР2.
