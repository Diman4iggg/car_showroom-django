# ЛР2. Автоматизированное тестирование CarShowroom

Дата: 16.10.2026.

## 1. Запуск

Все зависимости уже перечислены в `requirements.txt`. Из корня проекта в активированном окружении:

```powershell
python -m pip install -r requirements.txt
python -m pytest
```

Команда запускает существующие тесты Django и новые тесты pytest, измеряет покрытие строк и ветвей и проверяет порог 70%. При ошибке обычного теста, неожиданном исправлении известного дефекта или недостаточном покрытии процесс завершается с ненулевым кодом.

Для запуска отдельного уровня без пересчёта покрытия всей системы:

```powershell
python -m pytest tests -m unit --no-cov
python -m pytest tests -m integration --no-cov
python -m pytest tests -m scenario --no-cov
python -m pytest tests -m known_defect --no-cov -rx
```

Существующий `python manage.py test` продолжает запускать Django TestCase. Для всех новых параметризованных тестов и измерения покрытия следует использовать pytest.

## 3. Arrange–Act–Assert

В новых тестах этапы подписаны комментариями:

1. **Arrange:** фикстуры создают пользователя, автомобиль и заказ либо подготавливают входные данные и зависимость.
2. **Act:** вызывается функция, форма или HTTP-маршрут приложения.
3. **Assert:** проверяются возвращённый результат, HTTP-статус, сохранённое состояние БД и побочные эффекты.

В сценарном тесте каждое действие сопровождается проверкой состояния из БД, прежде чем выполняется следующее действие. Сценарий не разделяется между несколькими зависимыми тестами.

## 4. Параметризация и отрицательные проверки

`pytest.mark.parametrize` применяется к:

- дате рождения: 18 лет вчера, сегодня и завтра, несовершеннолетняя и будущая дата;
- телефонам: четыре допустимых кода оператора, неверный код, длина и пустая строка;
- форме оплаты: неверные номер, CVV, месяц, пустое имя и отсутствие согласия;
- сроку карты: предыдущий, текущий и следующий месяц;
- прогнозу: отсутствие данных, одна точка, рост, снижение и постоянные продажи;
- внешним API: сетевые исключения и ошибочные HTTP-коды;
- недопустимым переходам состояния и действиям чужого сотрудника.

## 5. Моки и HTTP-заглушки

В модульных тестах `unittest.mock.patch` заменяет источник текущей даты. `Mock` и `SimpleNamespace` заменяют объекты автомобилей: для пересчёта валют не нужна БД.

В HTTP-интеграционных тестах подменяется `requests.sessions.Session.send`. Остальные части цепочки настоящие:

```text
Django test client → view → service → requests.get
→ подготовленный HTTP-запрос → заглушка Session.send
→ requests.Response → разбор JSON → context/HTML
```

Заглушка возвращает настоящий `requests.Response`, поэтому `raise_for_status()` реально обрабатывает HTTP-коды. Проверяются URL, query string, метод и параметр `timeout=5`. Сетевые ошибки создаются исключениями Requests на границе транспорта.

Автоматическая фикстура `block_external_http` запрещает неожиданные HTTP-запросы в новых тестах. API-ключ тестовый, интернет и реальные внешние сервисы не требуются. Проверка настоящего сервера провайдера в эти тесты не входит.

## 6. Независимость

- Каждый тест с `django_db` получает изолированные изменения БД, которые откатываются после выполнения.
- Фикстуры имеют область действия одной тестовой функции.
- Пользователи и товары создаются в тестовой БД, без чтения рабочей SQLite и локальных фикстур данных.
- `monkeypatch`, `patch` и фикстура `settings` восстанавливают изменения после теста.
- Дата для граничных проверок фиксируется; сценарии не используют идентификаторы из предыдущих тестов.
- Для независимых пользователей при необходимости используются отдельные экземпляры HTTP-клиента с разными сессиями.
- Таймеры, sleep и порядок выполнения тестов не используются как условия успешности.

## 7. Связь с диаграммой состояний ЛР1

| Переход | Проверка |
|---|---|
| Начальное → `new` | Быстрая покупка через POST, создание позиций и уменьшение остатка |
| `new` → `new` | Принятие свободного заказа сотрудником |
| `new` → `confirmed` → `paid` → `delivered` | Один последовательный сценарий с проверками статуса, Sale и даты выдачи |
| Начальное → `paid` | Корзина и валидная демонстрационная оплата |
| `new` → `cancelled` | Отмена клиентом/сотрудником; повторная отмена не увеличивает остаток повторно |
| Запрещённые переходы | Например, `new → paid`, `confirmed → delivered`, `paid → cancelled`, `cancelled → paid` |
| Выдача онлайн-оплаченного заказа | Ожидаемо падающая проверка ISSUE-006: такой заказ пока нельзя закрепить за сотрудником |

## 8. Покрытие и отчёты

Конфигурация находится в `.coveragerc` и `pytest.ini`. Измеряются шесть прикладных Django-модулей. Из расчёта исключены тесты, миграции, служебные `__init__.py` и декларативная конфигурация (`apps.py`, `admin.py`, `urls.py`). Конфигурационный пакет `CarShowroom` не входит в измеряемые исходники. Команда `seed_demo_sales` включена в покрытие и проверяется отдельным тестом.

После запуска формируются:

- `htmlcov/index.html` — интерактивный отчёт по файлам, строкам и ветвям;
- `coverage.xml` — машиночитаемый отчёт;
- таблица покрытия в терминале.

Сгенерированные отчёты исключены из Git и воспроизводятся командой `python -m pytest`.

## 9. Известные ограничения

Проверка БД выполняется на SQLite тестового окружения. Семантика блокировок PostgreSQL и одновременная оплата несколькими процессами требуют отдельного запуска и конкурентных тестов на PostgreSQL; SQLite-тесты этого не доказывают.

Тесты известных дефектов имеют `xfail(strict=True)`: статус XFAIL означает воспроизведённое расхождение, а не успешную реализацию требования. Если дефект исправят, тест станет XPASS и остановит сборку, пока пометка ожидаемого падения не будет удалена. Новый ISSUE-006 зарегистрирован в `ISSUES.md`.
